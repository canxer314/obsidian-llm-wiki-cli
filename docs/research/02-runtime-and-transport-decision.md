# Runtime and transport decision for the Vault Operation Bridge

**Research date:** 2026-08-01  
**Decision:** use one **Obsidian-plugin-hosted Vault Operation Bridge**. The plugin is the single authoritative runtime for Vault semantics, Recovery Journal, Content Versions, search/index coherence, and the global Change Set executor. It exposes a **loopback-only Streamable HTTP MCP endpoint** (`http://127.0.0.1:<configured-port>/mcp`) directly to Claude Code. It is not an external filesystem-writing service and does not require a separately started daily daemon.

This is a plugin-plus-bridge composition, but the bridge is hosted in the already-running Obsidian plugin process for the MVP. It starts in the plugin lifecycle only after the configured ThinkFlywheel Vault is open, and stops during plugin unload. Claude Code connects to the endpoint from every Agent Session. If Obsidian/the Vault/bridge is unavailable, the endpoint returns a machine-actionable unavailable result; it never falls back to shell commands or direct filesystem writes.

## Fixed boundary used to decide

The design must support one open Windows Vault, CJK paths/content, multiple concurrent Claude Code Agent Sessions, structured tools, automatic startup, Obsidian `MetadataCache` and link semantics, immediate bridge-visible reads after a successful write, serial all-or-restore Change Sets, and durable crash recovery. It must not operate while Obsidian is closed or silently bypass it. These are the resolved product constraints in [Define the MVP product boundary and operating model](https://github.com/canxer314/obsidian-llm-wiki-cli/issues/3).

## Evidence

### Obsidian is the required semantic authority

The official API makes this in-process boundary explicit: `App` exposes `vault`, `metadataCache`, and `fileManager`, while an Obsidian plugin reaches the global App through `this.app`. [App declarations](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L406-L441); [plugin README](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/README.md#L37-L44). The public declaration/API surface provides no documented external-process call path to those services. That absence is an API observation; the conclusion that an external service needs a bridge/IPC is the resulting architecture inference, not a claim of an undocumented prohibition.

`Vault` supplies individual create/modify/rename/trash operations and `process(file, synchronousTransform)`, whose contract is an atomic read-modify-save of **one** note. The API directs a caller that will modify a file to use `read()` rather than `cachedRead()`. `DataWriteOptions` supplies only optional timestamps; it supplies neither global concurrency control nor a cache-visibility/transaction guarantee. [Vault mutation declarations](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L7394-L7534); [`DataWriteOptions`](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L2148-L2162).

`Vault.rename()` explicitly directs callers to `FileManager.renameFile()` when automatic link renaming is desired; `FileManager.renameFile()` is documented as a safe rename/move that updates links **according to the Primary Operator's Obsidian preferences**. `MetadataCache` supplies `getFirstLinkpathDest`, `resolvedLinks`/`unresolvedLinks`, backlinks, and file-cache access. [Rename declaration](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L7466-L7474); [`FileManager.renameFile`](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L2895-L2902); [`MetadataCache` link APIs](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L4404-L4444).

Two consequences are material:

1. A direct external filesystem service has neither the running app's `MetadataCache` nor its `FileManager` semantics, so it cannot meet the fixed link/cache boundary through a supported integration.
2. `FileManager.renameFile()` alone is insufficient: its link updates follow a user preference, while this MVP requires deterministic updates of every uniquely resolvable reference. The bridge must use cache-backed resolution in Change Set preflight, reject ambiguity, and include its own format-preserving reference edits in the Change Set; it may not claim the preference-dependent helper is a transaction or a complete semantic guarantee. `MetadataCache.changed` is not emitted for rename, so coherence logic must also observe the Vault rename event. [Obsidian API event declarations](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts).

The API offers asynchronous individual Vault operations, not a public multi-file transaction or a public "metadata cache is now caught up" commit barrier. Thus no candidate can inherit atomic Change Sets from Obsidian. The bridge must implement the required guarantees: one in-process global write queue, durable Recovery Journal written before the first mutation, preflight revalidation at dequeue time, inverse/restoration records, and recovery-before-writes on the next plugin load. It must only acknowledge success after its own authoritative post-write rereads/hashes and documented cache-coherence observation make the resulting Content Versions available to its subsequent tools. This is deliberately stronger than assuming an individual `Vault.modify()` return means every consumer's metadata cache is settled.

For cache readiness, the documented `metadataCache.changed` event means that a file is indexed and updated metadata is available, but it explicitly does **not** fire on rename; the bridge must additionally observe `vault.on("rename", ...)`. `metadataCache` also exposes per-file `resolve` and global `resolved` events for link-graph resolution. [Metadata cache events](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L4446-L4472); [Vault events](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L7567-L7593).

Deletion must similarly avoid preference-dependent helpers. `Vault.delete()` permanently deletes, whereas `Vault.trash(file, false)` selects the Vault's local trash; `FileManager.trashFile()` follows the user's configured trash preference. The Change Set executor must explicitly select the local-trash semantic required by the product rather than use either delete or a preference-controlled FileManager operation. [Vault delete/trash declarations](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L7450-L7465); [FileManager deletion declarations](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L2904-L2920).

Obsidian loads an enabled community plugin from the Vault's `.obsidian/plugins` directory. A Plugin extends Component, `onload()` may be async, and `registerEvent`/`register`/`registerInterval` provide unload cleanup. The API README permits desktop-only plugins to use Node/Electron `require`, but publishes no persistent external-service or external-process IPC lifecycle. It is therefore reasonable to host the MVP listener under plugin lifecycle; a separate service would require a deliberately designed bridge, not a supported call to private app internals. [Plugin packaging/runtime](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/README.md#L15-L35); [Plugin lifecycle](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L4901-L4929); [Component cleanup](https://github.com/obsidianmd/obsidian-api/blob/cc1744324150c632416857c98964f87b1574a5fc/obsidian.d.ts#L1835-L1912).

### MCP supplies a structured Unicode-safe interface

MCP messages are JSON-RPC and **must be UTF-8**, independent of transport. Tools are advertised through `tools/list` with JSON Schema input; `tools/call` can return JSON `structuredContent`, validated against an advertised `outputSchema`. Therefore note contents, paths, versions, errors, previews, continuation tokens, and Change Set states stay in typed JSON bodies rather than PowerShell command strings. [MCP transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports); [MCP tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

This removes the relevant CJK failure mode: the bridge and Claude Code must encode/decode JSON as UTF-8 and preserve note bytes/newline form in tool payload fields. It must never put note content or arbitrary CJK values in HTTP headers. The HTTP transport has special header-value encoding, whereas ordinary tool parameters belong in the JSON body. [MCP Streamable HTTP value encoding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#value-encoding).

### Why loopback Streamable HTTP, not stdio

For stdio, the MCP client launches the server as a subprocess; messages are newline-delimited JSON-RPC over stdin/stdout and stdout may contain only protocol messages. This is excellent for a client-owned one-session helper, but each concurrent Claude Code session owns a separate process and its lifetime. It does not create the single shared executor needed here. [MCP stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio). Claude Code documents local stdio servers as local processes and does not automatically reconnect a disconnected stdio server. [Claude Code MCP: local stdio](https://code.claude.com/docs/en/mcp.md#add-a-local-stdio-server).

Streamable HTTP instead defines an independent server capable of handling multiple client connections. Each Agent Session gets its own protocol connection, while all requests enter the same plugin-hosted executor and therefore share the same serial Change Set queue, Submission-Key deduplication state, Recovery Journal, and coherent search/read view. Claude Code supports this configuration as `type: "http"` (and accepts `"streamable-http"` as an alias) and retries HTTP/SSE connection failures, unlike stdio disconnections. [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [Claude Code MCP: HTTP servers](https://code.claude.com/docs/en/mcp.md#add-a-remote-http-server).

Use a fixed, installation-configured endpoint only while the configured Vault is open. Claude Code's personal configuration should be at `local` scope for this Primary Operator, not committed project configuration; the non-secret endpoint definition may use `user` scope if the Operator needs it across projects. Claude Code records local/user scope server definitions in the user's `~/.claude.json`; project `.mcp.json` is collaborative and subject to approval. [Claude Code MCP installation scopes](https://code.claude.com/docs/en/mcp.md#mcp-installation-scopes).

### Loopback security and lifecycle

The server binds exclusively to `127.0.0.1`, validates `Origin` on every connection, and requires an installation-generated bearer secret in the MCP configuration. These are not optional hardening: the MCP specification says local HTTP servers should bind localhost, should authenticate connections, and must validate Origin to prevent DNS-rebinding attacks. [MCP Streamable HTTP security requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

The server's authentication identity is a local transport guard, not an Agent Session identity. Tool inputs carry an Agent-Session/Submission-Key identity, and the bridge independently records it for idempotency and queue/status authorization. Reject requests without the secret, wrong Origin, unsupported Vault identity, invalid JSON/schema, or a write while recovery is pending.

## Options compared

| Composition / transport | Meets the boundary? | Decision |
| --- | --- | --- |
| **Plugin-hosted loopback Streamable HTTP MCP bridge** | Yes. It is automatically available when the required running Vault/plugin is available, holds the Obsidian API/cache, accepts multiple Agent Sessions, and avoids shell quoting. The bridge owns serialization, journal, and cache-readiness. | **Choose.** |
| Plugin-hosted stdio MCP | No for the normal multi-session case. Claude Code spawns it per client session, producing multiple independent queues and process lifetimes. A shared store/lock could mitigate this, but recreates an unnecessary companion protocol and does not improve Obsidian access. | Do not use as the primary transport. It is an acceptable one-session diagnostic adapter only. |
| External local service that reads/writes the Vault filesystem | No. It bypasses the only runtime with `MetadataCache`/`FileManager` semantics and cannot guarantee the app's immediate view, link behavior, or safe cache coherence. | Reject. |
| External MCP daemon plus an Obsidian plugin RPC endpoint | Conditionally capable, but adds a second process, local IPC reconnect/startup/security, and a failure mode between the transport and semantic authority. The plugin must still own every semantic operation, queue, and journal. | Defer. Use only if a prototype proves that hosting compliant Streamable HTTP in the plugin is not viable. |
| Separate daemon connected to plugin through Windows named pipes | Viable contingency, not MVP. Node supports Windows named-pipe IPC, but it is stream-framed and pipes disappear when the last handle closes; it adds framing, supervision, ACL, and reconnect work without adding Vault semantics. [Node `net` IPC documentation](https://nodejs.org/docs/latest-v26.x/api/net.html#ipc-support) | Do not select. |
| Custom MCP transport / PowerShell wrapper | No benefit. Custom transport reduces Claude Code interoperability; PowerShell introduces command quoting/code-page/lifecycle surfaces even though MCP already transports UTF-8 structured JSON. | Reject. |

## Required seams and invariants

1. **MCP gateway:** validate HTTP/MCP protocol, Origin, bearer secret, input/output schemas, and request cancellation. Return structured machine-actionable errors; do not turn note text into command-line arguments.
2. **Vault authority:** the plugin's single execution context owns every cache query and mutation. No gateway code may directly mutate the Vault directory.
3. **Read/search path:** concurrent read-only requests use plugin-held metadata/index snapshots identified by Content Version. A successful Change Set updates the bridge's authoritative view before further reads/searches observe success.
4. **Change Set executor:** all submissions enter exactly one FIFO serial queue. It rechecks target Content Versions and declared Read Dependencies immediately before execution. Submission Key equality returns the prior queued/executing/final result; a reused key with different canonical request content is rejected.
5. **Recovery:** persist the Recovery Journal before mutation; on plugin load or HTTP restart, finish restoration or surface recovery failure before accepting another write. The journal is operational state, removed only after success or completed rollback.
6. **Rename/link path:** use `MetadataCache` for canonical resolution and backlinks, reject ambiguous references, and execute deterministic format-preserving edits as part of the same Change Set. Do not delegate the guarantee solely to a preference-controlled FileManager helper.
7. **Availability:** the health/status tool exposes the configured Vault identity, plugin/bridge readiness, cache generation, queue/recovery state, and local endpoint version. If Obsidian closes or the wrong Vault is open, tools fail explicitly.

## Deferred validation

Before implementation, prototype the chosen plugin runtime against the installed Obsidian release: lifecycle start/stop, loopback listener behavior, concurrent HTTP MCP requests, CJK round-trip and original newline preservation, cache-event ordering for modify/create/rename, link handling with link-update preference both enabled and disabled, forced interruption at every journal phase, and two simultaneous Claude Code sessions submitting stale/read-dependent Change Sets. This is validation of the selected composition, not permission to weaken the stated guarantees.
