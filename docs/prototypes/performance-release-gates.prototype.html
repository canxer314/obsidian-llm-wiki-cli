MVP 性能发布门槛

点击场景，感受“工作已经做完”与“Change Set 已被证明成功”的差别。本页不运行真实 Vault，也不是性能证据；它只让测量协议与发布判定变得可评判。

本原型回答的问题： 什么固定 fixture、计时边界、参考环境、预热与重复程序、分位数和阈值，能把 warm discovery/read 与约 20-note validation/execution 目标变成发布门槛，同时绝不削弱 Content-Version-bound cache/graph success barrier？

推荐：双时钟，而不是二选一

Work Clock
从空队列中的 Change Set 成为 FIFO 队首、executor 开始 lease-time preflight，到 mutation 后的 exact raw-byte verification 完成。目标：每批 p95 < 1,000 ms。
Proof Clock
与 Work Clock 同一起点，到最终 Content Version 证据、图谱后置条件、250 ms quiet window、successor Search Snapshot 和 synced COMMITTED 全部完成。目标：每批 p95 < 4,000 ms；每次必须 < 5,000 ms。
关键：Work Clock 通过，只代表工作预算达标，不代表 Change Set 可以返回 intent_applied。只有 Proof Clock 完成，才能承认成功。

客户端与 Bridge 的边界

  • Discovery/read 发布门槛使用固定 benchmark MCP client 的 loopback round-trip：发送完整 Streamable HTTP 请求前开始，完整 MCP result 解码后停止。
  • Bridge server span同时记录：完整请求已解码并进入 tool handler，到 compact result 编码并交给 HTTP writer；它用于定位回归，不替代 client-observed gate。
  • Claude Code spot check单独记录工具调用往返兼容性，但不混入 p95；Claude 推理、工具选择、Claude API 网络、文本渲染均不属于 Vault Operation Bridge 的处理预算。
  • Change Set clocks取 Bridge monotonic lifecycle timestamps；status polling 的间隔和 Claude Code 是否立即继续推理不影响判定。

候选 release contract

固定 warm discovery/read fixture

  • 生成根：.mvp-perf-fixture/read-v1/；seed：mvp-perf-read-v1；每次注册 canonical manifest SHA-256。
  • 1,000 个 Markdown notes：500 × 2,608 B；449 × 10,240 B；50 × 29,316 B；1 × 163,904 B，总计 7,531,464 B。
  • 固定 tag/link/text graph；common discovery 组合 path prefix、正文 token、tag 与 outgoing-link 条件，确定性返回 20 条 path + Content Version + byte size。
  • common read 对这 20 个 median notes 执行有序完整 Exact Read；总结果低于 256 KiB，不创建 continuation，不允许截断或换行/Unicode 归一化。
  • 每批 Obsidian 重启后等待 ready，执行一次不计时的 snapshot materialization，再做 5 次不计时 warm-up，随后 30 次测量。

固定 20-note Change Set fixture

  • 生成根：.mvp-perf-fixture/change-v1/；seed：mvp-perf-change-v1；固定 manifest SHA-256。
  • 恰好 20 个既有 ordinary Markdown notes；每个 4,096 B、UTF-8 no-BOM、LF、固定 Frontmatter 与已解析 links。
  • 一个 Change Set 对每个 note 执行一次 plain-body replace_exact；每个 old text 唯一，closure 固定为这 20 个 notes，不含 attachment、rename、create/delete 或 derived rewrite。
  • fixture reset 与 inventory/hash verification 在每次样本之外完成；每次测量前 FIFO 必须为空，不能把排队时间偷算成 executor 性能。
  • rename、rapid overwrite、closure growth、link repair 与 timeout 仍由独立 correctness corpus release-blocking；不拿这些较重场景冒充“ordinary 20-note”基线。

Reference profile：MVP-PERF-REF-1（候选）

每批开始前：接通 AC、Windows “最佳性能”、Bridge-only Obsidian profile、无其他 Vault writer；连续 60 秒 CPU 平均低于 10%，可用内存至少 8 GiB。不得关闭 Defender 或其他正常系统安全措施。环境不满足时整批作废，不删除慢样本。

    引导场景

    你实际需要判断的四件事

    1. 固定 workload 是否代表“common / ordinary”？ 推荐把复杂 rename、derived rewrite 与故障注入留给 correctness corpus，不让基准定义被最坏情况劫持。
    2. 三批 × 30、每批 p95 是否足够稳定？ 推荐所有三批分别过门，不把 90 次混成一个分位数，也不删除 outlier。
    3. 完整成功 p95 < 4,000 ms 是否合适？ 它给已观测约 0.97–1.99 秒的 barrier 留出环境余量，同时仍明显早于 5 秒 fail-closed deadline。
    4. 当前工作站是否应成为唯一 reference machine？ 推荐先注册它为 MVP-PERF-REF-1；更慢硬件只有在另行注册 runtime profile 后才形成额外发布义务。
